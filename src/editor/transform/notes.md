# transform/

## Purpose

Transform gizmo system for interactive translate, rotate, and scale operations.

## Key Types

- **`Transform_tool`** -- Coordinates the three sub-tools (move, rotate, scale). Manages gizmo visualization meshes, handle hit detection, and drag state. Subscribes to hover and selection messages. Binds keyboard shortcuts for switching between transform modes and toggling coordinate space (local/world). Hover previews (rotation plane circle + disc for a ring) show pre-drag only; axis handles have no hover preview (the infinite axis guide line was dropped as noise), and the plane-translate hover grid was dropped in favor of Handle_visualizations showing both direction arrows of the plane's two axes while the sector is hovered. During an active translate drag `render_translate_drag_guides()` draws the NODE's travel: the traveled segment (axis drag) or an axis-aligned rectangle + diagonal spanning the anchor's initial and current positions (plane drag; edges color-coded per axis, diagonal yellow), 1 px, reduced alpha; the yellow segment / diagonal gets a short end-stop marker line across each end, orthogonal to it in screen space. `render_drag_readout()` adds drag text: translate shows bare coordinate values - initial position at its own window projection, yellow delta at the travel midpoint (hidden when its ink box would run into the initial or current label, same policy as the rotate delta label), current position below the hover mesh name (mirrors Hover_tool's +50 px x anchor and 16 px line step, so it needs a valid hover and the viewport path); scale shows labeled initial/current anchor scale under the gizmo; rotation text is drawn by `Rotate_tool::render()`. `Transform_tool_config::translate_snap_absolute` (default on; checkbox in the Transform window's Move tool group) makes translate snapping land the anchor's resulting position coordinates on snap multiples instead of snapping the drag delta; all translate snapping happens component-wise in the ACTIVE space's basis (world components in Global, anchor-frame components in Local / Reference), mapped back to world after. `Transform_tool_config::translate_cast_rays` (default off, Settings window) enables a translate-drag debug visualization: rays cast from each dragged node along the world axes, nearest hits marked with purple lines (like the physics tool's drag visualization; `render_rays()`).

- **`Move_tool`** -- Subtool for translation. Renders axis arrows and plane handles. Computes translation from pointer ray intersection with the appropriate constraint plane/line.

- **`Rotate_tool`** -- Subtool for rotation. Computes rotation angle from pointer position relative to the gizmo center. During an active drag `render()` draws a protractor in place of the gizmo ring: radius = view scale * `Transform_tool_config::rotate_ring_size` (default 4.0 = the gizmo rings' own radius; slider in the Transform window), a black background disc behind the whole protractor (`rotate_background_alpha` codegen setting, 0 disables; depth-tested visible-pass-only on stencil reference 1, so it never covers geometry in front of the rotation plane while every protractor line draws over it), thin (1 px) axis-colored ring, step markers on a fixed grid (small every 5 deg, medium every 10 deg, major every 45 deg; thinner than the spokes/ring; inner radii scale with the ring) and the two indicator spokes (initial and current = initial + snapped angle). `Transform_tool_config::rotate_snap_absolute` (default on; checkbox in the Transform window's Rotate Tool group) makes rotation snapping land the resulting absolute angle (initial twist + delta) on snap multiples instead of snapping the drag delta. `Transform_tool_config::rotate_sector_anchoring` (enum, Settings window) picks the protractor frame: Drag Relative anchors the initial spoke to the pointer position at drag start; Axis Absolute anchors theta = 0 to the active space's plane side, so the spokes sit at the anchor's absolute twist angles around the rotation axis (the drag delta amount is computed identically in both modes). The swept sector is emphasized in yellow: 1.41 px ring arc (per-segment classification of one polyline, not overdraw) and in-sector step markers, plus a 0.14-alpha fill. Angle labels: initial and current (white) sit just outside the ring at their directions - initial is the swing-twist decomposition of the anchor's start orientation about the rotation axis, current = initial + snapped drag angle (continuous past +/-180 deg); the on-screen upper label is bottom-anchored and the lower top-anchored (exact font measure bounds, framebuffer-origin aware) so they can never overlap. The yellow delta label sits on the sector bisector at the same radius with its ink box centered on the anchor (baseline anchoring would hang the text above the anchor, crowding the upper label while leaving room below), and is hidden when its box would intersect either label's box - a rect test, so horizontal separation counts as fitting just like vertical.

- **`Scale_tool`** -- Subtool for scaling. Computes scale factor from drag distance ratios relative to the gizmo center, so handle placement is free to move without affecting drag math. The basic-scale axis handles are cube-tipped shafts (cube vs the translate arrows' cone is the at-a-glance shape cue). Their placement composes with the `show_translate` TOGGLE, never transient drag hiding (placement must not jump mid-drag): with translate off they take exactly the translate layout (camera-facing side, `arrow_start` outside the rotate sphere, protractor-radius start during a rotate drag); with translate on, each axis line reads inside-out as rotate sphere -> translate arrow -> scale cube (shaft resuming past the translate cone tip after `scale_handle_gap`, running `scale_shaft_length`). During an active scale drag of an axis both directions of that axis are shown, mirroring the translate arrows' rule. Drag-time hiding (`hide_inactive`) is exact-match: only the handle whose axis mask equals the dragging subtool's mask stays up (so a uniform-scale drag keeps only the uniform wedges, not the per-axis scale handles), the translate-arrow pair and the rotate-drag arrow exceptions aside. Plane and uniform handles live INSIDE the rotate sphere as concentric shells, inside-out: uniform-scale wedge (the innermost sector of EVERY plane, starting at the center - the three wedges are together the one uniform handle, hovering and dragging as one), plane-translate annular sector (fill alpha 0.5), plane-scale annular sector (half fill alpha) ending `ring_sector_gap` short of the rotate ring radius (a larger gap than between shells, keeping the ring visually separate). The config radii (`uniform_scale_outer_radius`, `plane_translate_outer_radius`) define the all-visible layout; `get_plane_shell_layout()` reflows it from the tools' visibility TOGGLES (never drag hiding) - a hidden shell donates its space and the visible shells stretch proportionally, always keeping `plane_sector_gap` between neighbors and `ring_sector_gap` below the ring. Each sector's pick zone grows radially by half the gap, so pick zones never overlap. Drag-time constraint matching requires the handle's tool family besides the axis mask (translate_xy and scale_xy share a mask). In positive-only translate mode each plane's sectors span the camera-facing quadrant; in negative-handles mode they are full annuli. With the plane shells always ending at the ring radius, the axis arrows start at `arrow_start` in every mode (the old fixed-octant quad-end start is gone).

- **`Subtool`** -- Base class for transform sub-tools with shared handle visualization logic.

- **`Handle_visualizations`** -- Draws the gizmo handles (arrows, plane quads, rings, scale cones/cube) with the debug primitive renderer (x-ray lines and filled triangles; no scene meshes) and hit tests them analytically (`pick()`). Rendering and picking share the same per-handle visibility rules, so a handle is pickable exactly when it is drawn. `pick()` takes the eye separately from the intersection ray: view-dependent shown/hidden choices (camera-facing arrow, quad quadrant, ring-arc occlusion, view-ring plane) use the camera node position - one mono decision, in XR the head, shared by both eyes even if slightly off per eye - while intersection runs on the control ray (in XR the controller aim ray). On desktop viewports the two coincide. The view-ring drag plane (Rotate_tool view mode) uses the same camera eye so the drag measures angles in the plane the ring is drawn in. Text readouts are window-space and are skipped when `context.viewport_scene_view` is null (headset render context) - no gizmo text in XR for now. The XR controller ray (Headset_view::render) gets its gizmo feedback through Transform_tool accessors, because the meshless gizmo never appears in the hover slots: `get_hover_handle_position_in_world()` (first hit on a visible handle; the arcball region and box faces are excluded), and `intersect_rotate_sphere()` entry / exit / first-axis-plane-crossing points. The ray draws x-ray (never depth-dimmed): light gray to the sphere entry or handle, cyan inside the rotation sphere, dark cyan after crossing the first gizmo axis plane, stopping at the first visible handle hit or the sphere exit. The translate presentation is view-dependent: without negative handles, each axis shows the one camera-facing arrow (placed outside the rotate-ring sphere so arrows and rings never contest the same radius) and each plane quad sits at the gizmo center extending into the camera-facing quadrant (min corner on the center, so the three quads share edges). The camera-facing octant selection is always active, whether or not the rotate rings are shown via the show_rotate toggle (the plane sectors would otherwise render into a quadrant facing away from the camera). Draw order is inside-out (quads, rings, arrows) because the x-ray debug lines layer by submission order (first-wins per pixel: stencil greater/replace at a shared reference, so it only orders draws within one bucket - line vs triangle buckets have no defined mutual order). The translate axis arrows render through their own stencil-reference-3 buckets so their pixels always land in front of the reference-2 gizmo pixels (rings in particular); pick() matches by never letting a ring take the pick from a ray that already hit a translate arrow. Every rotate ring is hidden during ANY active drag (the drag-time axis-mask match would otherwise keep the same-axis ring up during axis translate/scale drags); the rotate protractor / travel guides replace them. In visible-arcs mode only SHOWN rings occlude arcs; the single-shown-ring presentation (full circle + tangent/bitangent guides fading in from the center) is currently unreachable because drags hide all rings. Two optional Houdini-style rotate handles (both codegen settings, Settings window): `rotate_view_ring` (default on) draws a light gray camera-aligned ring outside the rotate sphere (`e_handle_rotate_view`, `Axis_mask::view`) whose drag rotates around the viewing axis (Rotate_tool view mode: plane normal = eye-to-anchor); `rotate_arcball` (default on) makes a ray inside the rotate sphere that hits NO other handle pick `e_handle_rotate_free` (`Axis_mask::free`, lowest pick priority - it never goes through the nearest-t comparison), dragging it arcball-rotates (pointer mapped to a virtual sphere of the gizmo radius, silhouette-clamped outside; no protractor is drawn). Hovering a handle (pre-drag; arcball excluded) dims every other handle's alpha by `hover_dim_factor` (codegen setting, default 0.4), except handles RELATED to the hovered one which keep full strength: a plane-translate hover keeps the axis arrows of the plane's two axes - showing BOTH directions of each (positive and negative, exempt from the single-arrow filter; the hovered handle itself is always exempt too, so hover can rest on an opposite arrow it brought up - pick() reads the previous frame's hover from Transform_tool for this) - while fully HIDING (alpha 0, regardless of the dim factor) the perpendicular translate arrow and every scale-axis handle, a plane-scale hover mirrors this for scale (the plane's two scale-axis handles show fully with both sides; the perpendicular scale handle and every translate arrow hide fully; hovering a scale-axis handle itself also shows both its sides, since one handle covers both directions), a rotate-ring hover keeps the translate arrow along the rotation axis, a uniform-scale hover keeps every scale handle while fully hiding all translate arrows. Sector outlines draw ONLY on the hovered/active sector handle - at rest the whole sector stack is fill-only (the uniform-scale handle counts as one: hovering it outlines all three wedges). At `hover_dim_factor` 0 the dimmed handles are skipped entirely in render (never in pick - they must stay pickable for hover to reach them). Per-axis handle colors are codegen settings (`axis_color_x/y/z`), as are the hovered/active handle colors (`hover_color_x/y/z`, `hover_uniform_scale_color`, `hover_view_ring_color` - defaults are 2x the base colors; the hot color replaces the base outright, fills and outlines alike); the drag-time emphasis colors used by the protractor and the rotate hover highlight (`get_axis_color()` in handle_enums.cpp) are the codegen `active_color_x/y/z/view` settings (defaults are 2x-bright axis colors - components above 1 over-brighten when blended; plane masks map to their perpendicular axis). The solid tips are flat-shaded: translate cone lateral triangles and scale cube faces modulate by a fixed world-space light (ambient 0.55 + diffuse 0.45, constants in handle_visualizations.cpp), and the translate cone's base disc darkens by a fixed 0.5 to read as the underside.

- **`Handle_enums`** -- Enumerations for handle types (axis, plane) and coordinate spaces.

- **`Transform_tool_settings`** -- Settings for gizmo behavior (snap, local/world space).

- **`Rotation_inspector`** -- Debug window showing rotation decomposition.

## Public API / Integration Points

- `Transform_tool` is registered as a tool and activated from the hotbar
- `Transform_tool::update_target_nodes()` resolves the selection to the nodes the gizmo actually drives, via `resolve_transform_target()`. This is identity for everything except a skinned mesh whose joints live outside its own subtree: glTF 2.0 requires skinning to ignore the mesh node's transform (and erhe's `Joint_buffer` / `standard.vert` do), so dragging the host node would move the gizmo and leave the mesh in place. Such a selection redirects to `erhe::scene::get_skin_transform_root()`, and the Transform window shows a note naming the driven node. Targets are de-duplicated, so several meshes sharing one skin produce a single entry (otherwise a drag would apply its delta once per mesh). Selection itself is untouched - the host node stays selected, so delete / duplicate / Properties keep acting on what the user picked.
- Creates `Node_transform_operation` entries on the operation stack for undo/redo
- Uses `Time::begin_transform_animation()` for animated transform transitions
