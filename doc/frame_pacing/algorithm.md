# Frame Pacer - Algorithm

Stability: stable

The normative frame pacing algorithm, verified against the control-theory model in [control_model.md](control_model.md). [`scripts/frame_pacing_sim.py`](../../scripts/frame_pacing_sim.py) is the executable reference model and `erhe_frame_pacing_tests` its C++ parity suite; both run every claim by number, and both stay green across any change to the algorithm. Section 8 lists each claim with its scenario and result; the deviations list after it records where the algorithm refines the model.

Several claims name conditions the integration met rather than the model predicted: C10 and C11 (heavy-tail flapping and slot-cursor drift while the pacer ran as an observer), C12 (the tracked grid), C13 and C14 (a dropping `fifo_latest_ready` presentation path), C15 (a presentation engine that accepts target present times and ignores them - see [nvidia_present_timing_driver_report.md](../reference/nvidia_present_timing_driver_report.md)), C16 (a grossly wrong queried refresh period, issue #2 of the same report), C17 (scanout-side display skips, with the negative finding that skips alone do not reproduce the live cadence amplification) and C18 (its actual mechanism: the inline present-request holdback gating the next decision). C19 to C21 cover the tier S slop servo. C22 (a target-honoring compositor whose presentation deadline lies more than a refresh period before the vsync, measured on macOS) motivates the deadline offset estimator of section 3.3; C23 (a GPU that clocks down at the longer cadence) the quantile upshift test of section 5, C24 (the same GPU on a FIFO compositor with a 2T deadline, measured on a ProMotion panel) the cadence-scoped predictive downshift and the FIFO anchor, C25 (that GPU's and the CPU's clocks measured per frame) the clock-aware upshift test and C29 (a light workload's idle clock recorded at a cadence) its per-workload clock records, C26 (the governor's ramp after an upshift) the GPU pre-warm, C27 (that ramp recorded as the shorter cadence's clock) the steady clock records, and C28 (an earlier visit's latency samples and queue waits counted as latency) the per-visit latency windows. C30 (a variable refresh rate display, measured on an Adaptive-Sync panel in fullscreen) motivates the display kind of deviation 24. C31 (a load just inside one period there, whose GPU clocks down at N=2) the cadence tests' VRR forms of deviation 25.

Notation follows the model document (`T`, `N`, `j`, `d_k`, `r_k`, `L`, `s`, `m`, `q`, `W`, `H`, `T_up`, `M`, `Q*`, `F`).

## 1. Interface (backend agnostic)

The pacer is a pure, engine-independent object driven entirely through this interface. It never calls the OS, Vulkan, or a clock itself - the integration layer feeds it timestamps and executes its decisions. That is what makes it unit-testable against a virtual clock (requirements: Isolation and testability) and portable across Windows/Android backends.

```
schedule(frame_id, now) -> {
    release_time,        # earliest time the app may start per-frame work (FR2)
    target_slot,         # vsync slot index in the pacer's estimated grid
    target_time,         # requested presentation time, passed to the API (FR3)
    predicted_display,   # FR4: when this frame will be shown ...
    predicted_duration,  #      ... and for how long (N*T)
    N,                   # cadence used for this frame
    wait_id              # FR5: block release until this frame id has displayed
}
on_cpu_done(frame_id, cpu_duration)
on_gpu_done(frame_id, gpu_end_time, cpu_dur, gpu_dur, latency)   # latency = gpu_end - actual release
on_present_feedback(frame_id, achieved_present_time)
set_min_vsyncs(n)                    # FR1: application-set minimum
notify_swapchain_recreated()         # FR7
```

Integration mapping (sourcing details in [inputs.md](inputs.md)): `release_time` is the pacer wait; `wait_id` maps to `VK_KHR_present_wait` / present-timing wait; `target_time` maps to `VK_EXT_present_timing` / `VK_GOOGLE_display_timing` target present time; `on_present_feedback` comes from the same extensions' feedback; `on_gpu_done` uses calibrated GPU timestamps. In off mode (FR6 baseline unmet), `schedule` returns release = now, no target time, and no waits.

Input-fidelity contract (normative, parity with the verification simulation):

- `cpu_dur` and `gpu_dur` are stage **service times** - involuntary waits (pacer wait, fence, acquire) and GPU idle bubbles excluded per [inputs.md](inputs.md) section 3.2/section 3.3. Raw spans contaminate the outer-loop statistic `W` with pacing-induced wait time and can cause spurious downshifts.
- `on_gpu_done` shall be driven by **per-frame non-blocking polling** of the frame's timestamp bracket at the schedule point, not by the lazy fence-time read; C9 quantifies the graceful degradation if the lazy path is used anyway.

## 2. State

| State | Purpose |
|---|---|
| `phase`, `period` | Estimated vsync grid: slot time `V(j) = phase + j*period`. Both tracked from presentation feedback (deviation 10): real displays deviate from the queried refresh period (11 ppm measured), so a static-period grid drifts ~0.6 ms/minute |
| `period_ref`, `period_samples` | Gross-error re-seed (deviation 12): `period_ref` is the PLL clamp center (nominal until a re-seed replaces it); `period_samples` is a small window of period estimates from raw feedback deltas backing the re-seed decision |
| `N`, `dwell` | Current cadence; accumulated upshift headroom time |
| `m` | Safety margin (AIMD-adapted) |
| `c_win`, `g_win` | Sliding windows (length = history, 120) of CPU/GPU stage durations |
| `L_win[N]` | Per-cadence sliding windows of measured release->GPU-end latency, involuntary waits excluded, current visit only (C28) |
| `j_next`, `last_slot` | Slot cursor for the next target |
| `last_fb` | Latest presentation feedback: (frame id, achieved slot) |
| `consec_miss`, `streak_attr` | Self-miss streak length; min over the streak of per-frame max(c, g) |
| per-frame records | Ring buffer of the event timestamps required by the requirements document (also the data source for every window above) |

All estimators are **sliding-window order statistics** over the frame-record ring buffer, not constant-gain recursive trackers. This is a refinement of the model document (which described pinball-gradient trackers): the window quantile is exact, deterministic, needs no gain tuning, drops stale data completely `history` frames after a change point, and its steady-state ripple takes the role of the tracker ripple in the model's stability argument (C8 verifies ripple < `H`, measured headroom ~= 4x). A constant-gain tracker cannot be simultaneously fast enough downward for upshift detection and low-ripple enough for hysteresis; the window statistic plus the *per-frame* upshift headroom test (section 5) resolves that tension. The model's stability conclusions carry over a fortiori: the statistic is bounded, memoryless beyond the window, and has no feedback dynamics of its own.

Quantile convention: `q_p(win)` = the `ceil(p*n)`-th smallest of the `n` window samples (conservative upper realization), `p = 0.95`.

## 3. Inner loop - release scheduling (FR2, FR3, FR4)

```
schedule(frame_id, now):
    if completed_frames < K:                     # cold start seed phase, section 6
        j = max(last_slot + 1, first_slot_at_or_after(now))
        release = now
    else:
        budget = L_hat + m                           # L_hat = q_p(L_win[N]), fallback q_p(c)+q_p(g)
        j = j_next  (or first_slot_at_or_after(now) if unset)
        j = max(j, anchor(frame_id), last_slot + 1)          # section 3.1
        typical = L_hat_med + m                     # median latency (deviation 13)
        while V_hat(j) - delta_pe - typical < now - guard:           # unreachable slot: skip forward
            j += 1
        release = max(now, V_hat(j) - delta_pe - budget)
    j_next = j + N
    return decision(release, j, target_time = V_hat(j),
                    predicted_display = V_hat(j), predicted_duration = N*period,
                    wait_id = frame_id - 1 - Q*,
                    hold_until = V_hat(j) - period + guard)    # C15 request holdback deadline
```

The deadline is `d = V_hat(j) - delta_pe`; the release is `d - (L_hat + m)`, i.e. deadline minus predicted p-quantile latency minus adaptive margin - the pure prediction + margin servo of model section 6.2. Slot **reachability** uses the *median* latency `L_hat_med`, not the q95 budget (deviation 13): a spike-tail-inflated quantile must not skip slots the typical frame makes; a tail frame that does miss slips one slot and re-anchors, priced by the margin AIMD. `hold_until` is the C15 present-request holdback deadline, computed here so it uses the tracked grid; it is deliberately **not** capped to the next frame's release point (C18: the capped policy re-admits early displays whenever `budget > (N+1)*T - delta_pe - 2*guard`; past that bound only an asynchronous present decouples the holdback from the next decision). The present-wait clamp (`wait_id`) is enforced by the integration layer before the app starts; it is the FR5 hard invariant and is active from frame 0, including the seed phase and under corrupted estimates (C6: pending never exceeded `Q* + F`; measured max 2 of bound 3).

### 3.1 In-flight-aware anchoring

`anchor(frame_id)`: starting from `achieved_slot(last_fb)`, each frame scheduled after the fed-back frame advances it to `max(anchor + 1, min(target_slot_i, anchor + N_i))` - the frame displays at its target, no earlier than one slot after its predecessor and no later than its cadence after it (deviation 16) - then plus `N` for the frame being scheduled. The cadence cap belongs to a dropping queue (`Frame_pacer_tunables::present_queue` `dropping`, `fifo_latest_ready`, C13); on a FIFO queue (`fifo`: every queued image displays, at its target or later - Metal tier M) each in-flight frame advances it to `max(anchor + 1, target_slot_i)`, because a target the reachability test skipped forward lies beyond its cadence, and capping it there gives the next frame that same slot (deviation 18, C24). Targets below the anchor are guaranteed to slip because the display cursor (FIFO) is already past them.

**The anchor is authoritative, not a lower bound (observer-mode finding, C11):** once feedback exists, `j = max(anchor, last_slot + 1)` - the internal cursor `j_next` is used only before the first feedback arrives. Taking `max(j_next, anchor)` lets the cursor ratchet ahead of reality without correction whenever the app runs faster than the schedule (observer mode, or any future scheduling error), producing unbounded prediction drift.

This formulation is a correction discovered during verification. The naive re-anchor - "on slip feedback, bump `j_next` to achieved + N" - is insufficient: it ignores frames already in flight whose targets are equally stale. The failure mode is severe and silent: after a single cold-start or spike slip, *every* subsequent frame displays exactly one slot after its target, indefinitely. Cadence looks perfect (all durations = `N*T`), so nothing recovers; meanwhile the release schedule sits one period early, the present-wait clamp binds every frame, and the effective safety slack collapses to noise (~41 % believed misses in the unfixed simulation). The in-flight-aware anchor removes the stale targets in one step: one frame shows `2*N*T` while the skipped slot drains, then the schedule is back in sync (C1: zero slips, zero misses over 16 s simulated).

### 3.2 Margin adaptation

On each `on_gpu_done`, with believed slack `s = d - gpu_end`:

```
if s < guard:  m <- min(m_max, m + Delta_inc)        # miss or near-miss: fast attack
else:          m <- max(m_min, m - delta_dec)         # ample slack: slow release
```

Equilibrium near-miss rate = `delta_dec / Delta_inc` (AIMD fixed point). Defaults `Delta_inc = 0.10*T`, `delta_dec = 0.001*T` give ~= 1 % near-miss rate; actual slot misses sit well below that because the `guard`-wide near-miss band absorbs them (C1: 0 misses in 960 converged frames). `Delta_inc` trades recovery speed against the latency sawtooth: after a bump the margin decays over `Delta_inc/delta_dec = 100` frames, so larger `Delta_inc` means longer periods of conservatively early releases. The initial 0.25*T proposal produced a 4 ms sawtooth at 60 Hz; 0.10*T (1.7 ms) verified cleanly and is the revised default.

### 3.3 Deadline offset estimation

`delta_pe` comes from `Frame_pacer_tunables::deadline_offset_source`. With `fixed` it stays `deadline_offset_initial` (2.5 ms), the value for a presentation path whose late displays carry no deadline information: an engine that ignores target present times, paced through the C15 request holdback (there a display after the target follows from the request time, scanout skips and drops as much as from the GPU end). With `estimated` - the host declares a path that displays an image at the first refresh at or after its target and takes it when its GPU work ends (`erhe::graphics::Device::is_present_target_time_honored`, Metal tier M) - the pacer learns it from presentation feedback (C22):

- Each fed-back frame whose target slot was free (the newest earlier display lies before the target minus half a period) gives a sample: its completion margin `V_hat(j) - gpu_end` and whether it displayed more than half a period after its target. A frame behind a taken slot is a cascade and gives none.
- The last `history` samples, sorted by margin: the evidence is the largest margin of a late sample whose band (it and the `band - 1` samples of next smaller margin) holds at least `min_late` late samples, plus `guard`. A late frame at margin `x` proves the deadline lies before `x`; the band requirement keeps a single disturbance from counting.
- `delta_pe` rises at once to the evidence (a too-small offset displays frames late) and decays by `decay` per sample toward it (a too-large one only costs latency), clamped to `[deadline_offset_initial, 2*T]`. Once the late samples leave the window the decay probes downward; two late frames below the true deadline raise it again (C22: 4 slips in 11400 frames).
- The FR5 clamp counts the images the deadline holds in the queue by itself: `wait_id = frame_id - 1 - Q* - floor(delta_pe / (N * period))`. A frame must complete `delta_pe` before its vsync, so with `delta_pe` of a period or more it is released before frame `k - 1 - Q*` can have displayed, and the plain clamp would hold it past its deadline. With `delta_pe` below one cadence period the term is 0.
- Swapchain recreation resets the estimate (the presentation path may change).
- A host that measured the deadline (the Metal present calibration, [../erhe/metal_backend.md](../erhe/metal_backend.md) "Frame pacing") gives it as `deadline_offset_initial`, which is also the floor, and the ceiling as `deadline_offset_max` (the calibrated deadline plus T/2) instead of `2*T`; a ProMotion panel's deadline (about 2T + 1 ms) lies beyond the `2*T` ceiling.

## 4. Miss classification and attribution

Verification forced a sharper taxonomy than the model's single "miss" event; this table is normative for the implementation:

| Event | Definition | Consequences |
|---|---|---|
| **Self-miss** | `s < 0`: this frame's own chain finished after its deadline | Margin attack; counts toward the reactive streak |
| **Near-miss** | `0 <= s < guard` | Margin attack only |
| **Cascade slip** | Frame ready in time (or late only because serialized behind a predecessor in the GPU/present queue), displayed after its target | No margin/streak effect; handled by anchoring |
| **Timing-only miss** | Self-miss, but the streak's stage times fit the budget (`streak_attr + guard <= N*T`) | Margin/estimator problem: never a cadence response |

`streak_attr` is the **minimum over the current miss streak of each frame's `max(c, g)`**. Reactive downshift requires every missed frame in the streak to individually exceed the budget. Min-attribution is the second verification-driven correction: max-attribution lets a single spike's cascade misses (whose own stage times are normal) satisfy the threshold and downshift on an impulse, violating C5. With min-attribution, C5 holds (impulse: 3 disturbed frames, cadence unchanged) and C6 holds (60 frames of forced-zero estimates: misses every frame, cadence untouched, because the load evidence is absent).

## 5. Outer loop - cadence (FR1)

Evaluated once per `on_gpu_done`:

```
W = max(q_p(c_win), q_p(g_win)) + guard          # throughput statistic, model section 3.1
N_req = clamp(ceil(W / period), N_min_app, N_max)

if consec_miss >= M and streak_attr + guard > N*period:     # reactive downshift
    N <- max(N + 1, N_req);  reset streak
elif N_req > N:                                            # predictive downshift
    N <- N_req
elif N > N_min_app:                                        # upshift headroom
    x = max(c_k, g_k);  dwell_frames += 1
    if (N-1)*period - H < x <= (N-1)*period: dwell_loaded += 1      # hysteresis band
    if x > (N-1)*period or dwell_loaded > floor((1 - q_up) * dwell_frames): dwell, dwell_frames, dwell_loaded <- 0
    else: dwell += elapsed;  if dwell >= T_up: N <- N - 1
else:
    dwell, dwell_frames, dwell_loaded <- 0
```

Cadence budgets quantize by the **tracked** period, not the nominal `T` (deviation 12): with a grossly wrong nominal, load in the band between the true and nominal periods would otherwise look feasible at a cadence it cannot sustain - and the reactive path could never attribute the resulting misses (`streak_attr + guard` stays below the inflated nominal budget). Fraction-of-`T` tunables (`H`, margins, `guard`) keep the nominal scale.

- **The predictive downshift judges the current cadence by its own samples (deviation 17, C24):** `N_req` comes from `max(q_p(c), q_p(g)) + guard` over the stage times of the frames scheduled at the current cadence, needs `cadence_min_samples` (30) of them, and needs pressure (a miss or near-miss) from such a frame; every cadence change clears these samples. The GPU cost depends on the cadence (an Apple GPU clocks down at N=2): judged by the whole window, the longer cadence's slow frames and their near-misses sent the pacer straight back after every upshift. The reactive path guards the transition meanwhile. The whole-window `W` remains the latency seed and the C10 pressure record.
- **The work at the measured clocks (deviation 19, C25):** where the host reports each frame's GPU and CPU clocks as ratios of their maxima, the upshift test's stages are `g * gpu_clock / gpu_clock_next` and `c * cpu_clock / cpu_clock_next` - the frame's work, timed at the clock that processor showed at the next shorter cadence (the low decile of the clocks measured there for a similar workload - within `clock_record_work_band` of the frame's work, C29 - kept across cadence changes; the full clock before it has `cadence_min_samples` of them). Without a reported clock the stage is the measured time.
- **The clock records hold the steady clock (deviation 21, C27):** a cadence's clock samples start `clock_settle_time` (150 ms) after the first GPU end at that cadence; frames delivered after their cadence was left and frames that ran a pre-warm are not samples of it. The governor's ramp after a change is the previous cadence's state: recorded as the shorter cadence's clock, it predicts the work beyond that cadence's period and the upshift never completes again.
- The upshift test runs over **the frames of the current dwell**, not over the window, which keeps upshift immune to the window's ~2 s staleness after a load drop (C3: `T_up` + detection lag). A frame beyond the next cadence's period resets the dwell; a frame inside the hysteresis band below it (past `(N-1)*period - H`) is allowed for a `1 - q_up` share (`q_up` = 0.9) of the dwell's frames (deviation 15). The allowance lets the pacer leave a longer cadence on a GPU that clocks down there (C23); a heavy tail beyond the period still keeps the longer cadence (C10).
- **The cadence tests on a variable refresh rate display (deviation 25, C31):** with `display` `variable_refresh` the upshift test (and the pre-warm's switch test) has no hysteresis band - a frame predicted within the next cadence's period counts as headroom, a frame beyond it still resets the dwell. Both downshift paths are replaced by one backlog test: each frame at the current cadence updates `backlog = max(0, backlog + max(c, g) - N*period)`, and the pacer moves to `N + 1` when a frame adds to a backlog that earlier frames left and the backlog exceeds `N*period`. The upshift survival window (C10 backoff) is `4 * dwell_required` instead of `4*T_up`. An upshift that leaves the target spacing unchanged (both cadences beyond the spacing bound of deviation 24) switches without a pre-warm.
- **Upshift backoff (observer-mode finding, C10):** an upshift that is reverted by a pressure-driven downshift within `4*T_up` doubles the required dwell for the next upshift; an upshift that survives `4*T_up` resets it to `T_up`. At persistently borderline load the pacer therefore *probes* the higher rate geometrically less often (finitely many probes) instead of flapping, while genuine load drops stay fast (first upshift is always `T_up`).
- **Predictive downshift requires pressure evidence (observer-mode finding, C10):** `W > N*T` alone does not downshift - a miss or near-miss (`s < guard`) must have occurred within the last `history` completed frames. Heavy-tailed load whose q95 exceeds the budget can still be fully sustainable (the tail is absorbed by margin and queue elasticity); misses and near-misses are the honest sustainability signal, and the margin AIMD surfaces overload as near-misses well before frames drop.
- The reactive path is the fast-attack: decision after exactly `M = 2` observed self-misses (C2). The predictive path catches ramps with zero misses once pressure appears: the window quantile crosses after ~`(1-p)*history` ~= 6 elevated frames.
- Hysteresis `H` appears only in the upshift threshold; combined with `q_p`'s safe-side bias this parks borderline load at the higher `N` permanently (C4: 0 cadence changes over 40 s at a boundary-straddling load).
- On any cadence change: `dwell <- 0`; `L_win[N_new]` is cleared (a cadence's window holds the current visit, deviation 22) and the seed `L_hat` of the cadence left - floored by `q_p(c_win)+q_p(g_win)` only where that visit has fewer than `K` samples - floors `L_hat` and the typical latency until the visit has `K` samples of its own (carry-over is an overestimate when downshifting - safe); on upshift additionally `m <- m + Delta_inc` as a pre-emptive boost while the new cadence's latency distribution is learned (C3: zero misses through the transition).

## 6. Cold start, recovery, off mode (FR6, FR7)

- **Cold start**: first `K = 8` frames run open loop - release immediately, target the next free slot, collect records; the present-wait clamp is already active. Then engage closed loop with `N` chosen from the seeded windows. Measured time to steady state: 133 ms (bound 1 s).
- **Missed present**: never chase - a missed slot is re-anchored forward (section 3.1), not compensated by scheduling negative slack. The miss feeds margin/streak/estimators per section 4.
- **Swapchain recreation**: reset grid phase, `last_fb`, slot cursor, streak; **retain** `c/g/L` windows and margin (the load did not change). Measured recovery: 15 ms - effectively immediate, versus 133 ms cold (C7).
- **Off mode**: baseline extensions absent -> `schedule` degenerates to release-immediately with no target time and no waits; records still collected. No control claims.
- **`set_min_vsyncs(n)`**: raises `N` immediately if below the new floor; upshift never goes below `N_min_app`. Acts as a commanded downshift; no other special handling.

## 8. Verification results

Deterministic simulation: virtual clock, two-stage pipelined plant (`F = 2` frames in flight, fence at `k-F`, serialized GPU), FIFO presentation engine quantized to a true vsync grid the pacer does not know (3.1 ms initial phase error, true `delta_pe` 1.5 ms vs. assumed 2.5 ms), presentation feedback delivered at display time, all pacer inputs delivered only when causally available (a GPU completion is not visible to a schedule decision that precedes it). 60 Hz, Gaussian stage times, fixed seeds.

| Claim | Scenario | Result |
|---|---|---|
| C1 steady state | c~=6 ms, g~=8 ms, 20 s | PASS - N constant, **0/960** misses, 100 % frames visible exactly T |
| C2 step up | g 8->22 ms | PASS - decision after 2 observed misses; 6 late/slipped total during pipeline drain (bound M+2F+1 = 7); settle 193 ms; stays at N = 2 |
| C3 step down | g 22->8 ms | PASS - upshift 593 ms after drop (`T_up` + detection); 0 misses in transition |
| C4 borderline | g ~= 16.6 ms at T = 16.67 ms, 40 s | PASS - parks at N = 2, 0 cadence changes |
| C5 impulse | single g = 30 ms | PASS - 3 disturbed frames (spike + 2 GPU-queue cascade), cadence unchanged, margin returns to floor |
| C6 adversarial | L_hat and m forced to 0 for 60 frames | PASS - pending <= 2 (bound `Q*+F` = 3), no cadence response (attribution), recovery 15 ms |
| C7 cold start / recreation | empty state; recreation at 10 s | PASS - steady in 133 ms cold, 15 ms after recreation |

### Deviations from and refinements to the model document

1. **In-flight-aware anchoring (section 3.1)** - the model's re-anchor was underspecified; the naive form produces a stable-looking but permanently degraded one-slot-lag regime. Model section 3.3's "deadbeat correction" is achieved only by the in-flight-aware form. This is the highest-value finding of the verification.
2. **Min-over-streak attribution (section 4)** - required to keep C5 (impulse) and C2 (step) simultaneously satisfiable; max-attribution conflates cascades with load.
3. **Impulse/step physical bounds** - a spike disturbs `ceil((S - budget)/(N*T - g)) + 1` frames via the GPU queue, and a step disturbs up to `M + 2F` frames while the pipeline drains; the controller cannot recall in-flight frames. Model doc C2/C5 and section 7.3 updated accordingly. The *decision* latencies (2 observed misses; no cadence change on impulse) hold exactly.
4. **Windowed order statistics (section 2)** replace constant-gain quantile trackers, with the upshift condition moved to a per-frame test; C3 and C8 jointly confirm this resolves the fast-down/low-ripple tension the tracker could not.
5. **`Delta_inc` default revised** 0.25*T -> 0.10*T (section 3.2).
6. **Measurement-delivery contract (section 1)** - the nominal claims assume `on_gpu_done` arrives at the first schedule point after the GPU finishes (per-frame polling of the timestamp bracket). The lazy fence-read path is a verified graceful degradation (C9), not the nominal mode, and the service-time input definitions are normative - both were found in review, not in the original model.
7. **Pressure-gated predictive downshift (section 5, C10)** - found by observer soaking: the real editor's heavy-tailed load had q95 above the 2-vsync budget yet zero misses (tail absorbed by margin + queue elasticity); quantile-only downshifting flapped against the upshift path. The quantile is now an early-warning trigger only in the presence of recent (near-)miss pressure.
8. **Upshift backoff (section 5, C10)** - the per-frame headroom test can complete a dwell by luck under rare-tail load; each pressure-reverted upshift doubles the next probe's dwell (geometric convergence), a surviving upshift resets it.
9. **Anchor made authoritative (section 3.1, C11)** - found by observer soaking: with `max(j_next, anchor)` the slot cursor ratcheted ~49 s ahead of reality over minutes of unpaced running. Feedback now overrides the cursor outright.
10. **Dynamic grid: tracked period (section 2, C12)** - found by live measurement in the verification UI: the development display's actual refresh period is 11 ppm longer than the queried one, so a grid with the queried period drifts +10.3 us/s (~0.6 ms/minute, a full period every ~13 minutes) - visible as misaligned refresh lines in the UI and grid error across feedback gaps. The phase PLL gains a frequency branch (second-order PLL): the innovation, normalized per elapsed cycle, corrects the period estimate; outlier innovations (>= `guard`, i.e. slips/compositor hiccups) are excluded from the frequency branch; the estimate is clamped to +/-0.5 % of nominal; and every period change re-bases the phase so the slot nearest the feedback keeps its time (slot indices are absolute - an un-rebased period change of `dP` moves slot `j` by `j*dP`, which is seconds at real reference-clock epochs). The tracked period survives swapchain recreation (it is a display property). Grid consumers (UI refresh lines, FR4 predictions) must use the tracked pair, not the nominal period.
11. **Slot floor removed from the feedback path (section 3.1, C13)** - found by live inspection (frames 2836/2837 in the verification UI): with the app running faster than the refresh rate on `VK_KHR_present_mode_fifo_latest_ready`, superseded images are dropped and consume no display slot, but `j = max(anchor, last_slot + 1)` forces at least one slot per scheduled frame - the cursor ratcheted ~10 s ahead of reality (release times, targets, and believed slack all +10 s; margin pinned at the floor; miss detection dead). When feedback exists, the anchor is now the slot verbatim: its per-in-flight `+N` accounting already yields strictly increasing targets between feedbacks. The `last_slot + 1` floor remains only on the no-feedback path (cold start, feedback blackout, post-recreation). Release gating on such a runaway schedule would stall the app for the accumulated lead, so this fix is a precondition for enforcing releases at all.
12. **Gross-error period re-seed (section 2, section 5, C16)** - found live while testing app-driven fullscreen mode selection: after an SDL mode set to 23.976 Hz from a 120 Hz desktop, the driver reports `refreshDuration` = 43.478 ms (23.000 Hz) while achieved-present feedback shows the true period is 41.708 ms - a 4.2 % error ([driver report](../reference/nvidia_present_timing_driver_report.md) issue #2). The ppm-scale PLL (deviation 10) cannot recover: every innovation is pinned above the `guard` outlier gate (the frequency branch is completely dead) and the clamp band is centered on the wrong nominal, so the phase branch absorbs ~1.7 ms per frame forever. Fix: period samples from **raw feedback deltas** (`dt / round(dt/period)` - phase-independent, and immune to slips since a skipped slot moves `dt` and `dn` together); when the median of the sample window disagrees with the tracked period by more than 4x the clamp band, period and phase are re-seeded from the measurement and the clamp re-centers on the measured period (`period_ref`). Companion change: cadence budgets (`N_req`, reactive attribution, upshift headroom, predicted duration) quantize by the tracked period, not the nominal - see section 5. Delta-based estimation cannot distinguish integer-ratio aliases (e.g. a nominal at half the true rate); the re-seed handles fractional gross errors up to ~+/-30 % at `dn = 1`. The integration also routes the tracked period to the present-request holdback (C15): a holdback interval derived from the wrong queried duration can release the request before the previous vblank's deadline, defeating the mitigation.
13. **Typical-latency slot reachability + pacer-computed holdback deadline (section 3, C18)** - found live at 120 Hz N=3: the display ran a stable **4-slot cadence at planned N=3** with achieved == target (the pacer never saw a miss, margin at floor). Mechanism, reproduced in sim only after modeling the integration's thread structure: the C15 holdback runs **inline on the producer thread**, so the next frame's decision waits for the previous frame's present request (~`target - T`); with slot reachability judged by the q95 budget (spike-tail-inflated to ~31 ms against ~23 ms typical latency) the anchor slot was chronically "unreachable", the skip-forward fired every frame, and the schedule slid one slot into a self-sustaining longer cadence (at N=1: the alternating 1,2-gap sawtooth). Fix: reachability uses the **median** latency + margin; the q95 budget still sets the release. The holdback deadline `hold_until` moved into the schedule decision (tracked grid, deviation 12) and is deliberately not capped to the next release point - the sim rejected the capped policy (re-admits ~50-60 % early displays when `budget > (N+1)*T - delta_pe - 2*guard`). Past that budget bound the inline holdback is structurally lossy (tail frames slip; C18 accepts <= 9 % ~= spike rate); recovering both exact holdback and full-budget scheduling there requires presenting from a separate thread (same queue family, no ownership transfer - future work if measurements demand it). Live after the fix: mean gap 3.01, 0 early, N=3 stable.
14. **Estimated deadline offset and the deadline-aware FR5 clamp (section 3.3, C22)** - found live on Metal tier M: the macOS compositor honors target present times but latches an image about one refresh period plus 1.5 ms before its vsync. With the constant 2.5 ms offset every frame finishing inside that band displayed a refresh late while its believed slack stayed positive, so neither the margin AIMD nor the miss attribution saw anything: 40 % two-period displays at planned N=1. Learning `delta_pe` alone was not enough: the plain clamp (`wait_id = k - 1 - Q*`) released frame k only once frame k-2 displayed, two periods before k's target, which a deadline of more than one period plus the frame latency cannot fit. The model's estimator (control model section 6.1) is implemented for target-honoring paths only, because on the inert-target path late displays also come from request timing, scanout skips and drops (an all-paths estimator falsely raised the offset in C18 and re-created its 4-slot lock).
15. **Upshift headroom with a hysteresis-band allowance (section 5, C23)** - found live on Metal tier M: after a startup downshift to N=2 the Apple GPU span grew past the N=1 budget for a tail of frames and the per-frame upshift test reset the dwell on each of them; the pacer stayed at N=2. Frames inside the hysteresis band now count against a `1 - q_up` allowance, frames beyond the period still reset the dwell (an allowance for them too re-created C10's heavy-tail probing). Live this does not suffice yet: in later runs 15-30 % of the N=2 frames exceeded the whole period, depending on the schedule's phase ([../plans/frame_pacing_metal.md](../plans/frame_pacing_metal.md)).
16. **In-flight anchor from the in-flight targets (section 3.1, C10)** - the anchor added `N` per in-flight frame, assuming every in-flight frame sits `N` slots after its predecessor. Once two frames shared a slot (a cold-start miss), that rule re-created the collision every few frames: a limit cycle of target gaps (+4, +0, +2 at N=2) with late displays and the margin pinned at its maximum - C10's fixed seed missed 2 % in the C++-independent Python model with any upshift rule (found by a review of the C10 fragility). Each in-flight frame now advances the anchor to its own target slot, at least one slot (FIFO) and at most its cadence (a further target comes from an earlier schedule; on a dropping path taking it ratchets the cursor, C13). C10 seeds then miss at most 8/2160.
17. **Cadence-scoped predictive downshift (section 5, C24)** - found live on Metal tier M with the present calibration, on a ProMotion panel: the pacer upshifted from N=2 to N=1 and returned within 2-3 frames with no miss. The window still held the N=2 GPU tail (q95 about 10.5 ms, beyond T) and that tail's near-misses counted as pressure, so the predictive test judged N=1 by N=2's cost; at N=1 the GPU span is 5.9 ms with nothing beyond T. The predictive test now uses the stage times and pressure of frames scheduled at the current cadence only. Live: tier M holds N=1 in every launch (gate in [../plans/frame_pacing_metal.md](../plans/frame_pacing_metal.md)).
18. **FIFO anchor (section 3.1, C24)** - found live on the same path: after an upshift a target the reachability test skipped forward (its latency window held acquire-blocked N=1 latencies of an earlier N=1 stretch) lay beyond its cadence; the cadence cap of deviation 16 placed the next frame in that slot, the compositor displays every image, so it and its successor displayed late and the reactive path downshifted. On a FIFO queue the anchor follows each in-flight target.
19. **Upshift headroom from the work at the measured clocks (section 5, C25)** - found live on Metal tier M, Dell at 120 Hz: a varying share of launches (0-8 of 10 per batch) stayed at N=2 for good. IOReport showed the cause: at N=1 the GPU runs at 93-98 % of its maximum clock, at N=2 it is idle half the time and DVFS spreads it over 41-97 %, so ~5 ms of work took 6.4-8.1 ms median with a tail beyond the period, and every such frame reset the upshift dwell. A blind upshift probe broke C2, C3, C4 and C10 (stage times cannot tell a clocked-down GPU from heavy load). Where the host measures the clocks (`on_gpu_done` `gpu_clock_ratio` and `cpu_clock_ratio`, Metal: `Clock_monitor`), the upshift test judges `max(c * cpu_clock / cpu_clock_next, g * gpu_clock / gpu_clock_next)`, each `*_next` the low decile of that processor's clocks measured at N-1 (for a similar workload since C29) (kept across cadence changes) or 1 before N-1 has `cadence_min_samples` of them; the predictive and reactive downshifts keep the measured times. The CPU part followed in Debug: the P-cores drop to ~53 % of their maximum at N=2 and the CPU time rises ~1.7x with it.
20. **GPU pre-warm before an upshift (section 5, C26)** - found live on Metal tier M, Dell: with the clocks normalized (C25) the upshift fired, but over the first 6-7 frames at N-1 the GPU clock ramped from ~0.5 to ~0.8, frames displayed 1-2 refreshes late (visible judder) and the pacer reverted. A completed upshift dwell now first runs a pre-warm phase (`upshift_prewarm_seconds`, the host's ALU-only kernel after each frame, ordered after it): it switches once a frame's own times fit N-1's budget, doubles the fill when the phase ends with the clock below `upshift_prewarm_clock` (the governor answers the real workload only, so the fill is learned, not calibrated), and backs off when the clock rose but the work does not fit. Live: 2.3 ms after each N=2 frame raised the clock from 0.51 to 0.97 with the frame span back at 4.9 ms.
21. **Clock records from the steady state only (section 5, C27)** - found live on Metal tier M, Dell, in launches where the pre-warm kernel rate was not measured: the first upshift ran without pre-warm, its frames slipped while the clock ramped (0.45 to 0.78) and the pacer reverted. Those ramp frames entered N=1's clock record next to ~33 startup frames at 0.97, its low decile fell to ~0.58, the 5.1 ms of work at full clock was predicted at 8.8 ms - beyond the 8.33 ms period - and every frame reset the dwell: N=2 for good. A cadence's clock samples now start `clock_settle_time` after its first GPU end, and frames delivered after their cadence was left or that ran a pre-warm are excluded.
22. **Latency windows per visit, waits excluded (section 5, C28)** - found live on Metal tier M, Dell, all threading modes: after the upshift the pacer released every frame immediately for 85-120 frames; N=1's window still held the startup frames (scene load, 30-50 ms), and the frames, released early, waited in the FR5 clamp (6-15 ms), at the join and in `nextDrawable` - waits the latency input counted, so the estimate stayed at the N=2 level (22-30 ms against ~7 ms steady) and decayed only by creep. Release lost a refresh of latency; Debug, whose render thread is slower, skipped a slot in 20-30 % of the frames. The latency input `L_k` excludes the involuntary waits between release and submit (inputs.md 3.3), and a cadence change clears the entered cadence's window, seeding a floor instead of a sample (a seed kept as a sample had carried the startup spike down a chain of short visits).
23. **Clock records judged for the workload (section 5, C29)** - found live on Metal tier M, Dell, Bistro: the empty editor ran at N=1 with the GPU idling at 0.21 of its maximum clock (the governor answers the workload, not the cadence alone); the scene open downshifted to N=2, and N=1's clock record - all of it from the empty editor - predicted Bistro's 4.1 ms of work at full clock at 18 ms there, so every frame reset the dwell and the pacer stayed at N=2 although with the pacer off the same frames displayed one refresh apart. A clock sample keeps the frame's work (time x clock), and `at_next` judges N-1 at the low decile of the clocks of the samples whose work lies within `clock_record_work_band` (1.5x) of the frame's; with fewer than `cadence_min_samples` of them the stage is judged at full clock and the pre-warm (C26) measures the frame at the raised clock before the switch.

24. **The display kind: no grid on a variable refresh rate display (section 2, section 3.1, section 3.3, section 5, C30)** - found live on Metal tier M, fullscreen on a 48-120 Hz Adaptive-Sync panel: presented deltas sat at 10.6-11.8 ms or 16-20 ms while the GPU frame fit 8.33 ms, depending on the session's history. Late frames' ready-time deltas and the repeats below the 48 Hz floor (29.17 ms at N=3) fed the gross-error re-seed (deviation 12), which took them for the display period; from then on the display honored the pacer's own targets and confirmed the drifted period. Separately, the cadence tests' `guard` allowance (`W`, the reactive attribution) kept the live load (q95(g) + guard > T) at N=2. The host now declares the display (`Frame_pacer_tunables::display`, `Present_display_kind` `fixed_grid` | `variable_refresh`, with `max_refresh_interval`, which `variable_refresh` requires; through `Frame_pacing_observer::set_display`, whose change recreates the pacer). On `variable_refresh`: the grid period is `refresh_period` (the minimum refresh interval) for good - no re-seed and no PLL period branch; the phase follows on-time displays only, and a late display re-anchors the slot cursor to the first slot at or after it (re-basing the phase on it moved every in-flight target and cost more refreshes in the plant); no target lies more than `floor(max_refresh_interval / period)` slots after the previous target or the current slot, whichever is later (after a stall the stale target pinned every target behind its release while the cursor caught up one slot per frame), and the slot cursor, the FR4 predicted duration and the FR5 clamp's deadline images use that effective spacing when `N` exceeds it (a frame that cannot make that slot displays when it is ready, which costs only its lateness; reachability skips at N=2 and a cadence of N=3 otherwise spaced targets 25 ms apart and the display repeated the previous image in between: 271 of 509 heavy-phase deltas at 29.17 ms, 0 with the bound - a separate cap on `N` added nothing on top of it); the cadence tests drop `guard` (a late frame costs its own lateness, not a refresh); and a frame the display could not show at its target - within one period of the previous display, or more than `max_refresh_interval` after it (a repeat in between) - is a cascade for the deadline offset estimator, not a sample. `fixed_grid` (the default) is unchanged: every earlier claim's numbers are identical.

25. **The cadence tests on a variable refresh rate display (section 5, C31)** - found live on Metal tier M after deviation 24, fullscreen on the 48-120 Hz panel: Bistro clustered (7.5-7.7 ms of GPU work at full clock) held 120 Hz whenever it reached N=1 (span 7.67 ms, p95 7.70) but stayed at N=2 in 3 of 4 visits after the startup or a configuration switch. The N=2 frames' span tail (p95 10.8 ms) was all clock (span x clock never above 7.8 ms), so the clock-aware upshift test (deviation 19) predicted N=1 correctly; but half of the predictions lay inside the hysteresis band (`T - H` = 7.5 ms ... T), beyond the `1 - q_up` allowance of deviation 15, and the dwell reset. On a fixed grid the cadence tests price a frame past the period at a whole refresh: the band parks borderline load at the longer cadence (C4), the predictive downshift judges `q_p`, and two attributed misses are load. On a VRR display such a frame costs only its own lateness, and the cost of a cadence is the queue's backlog: the stage times' excess over the cadence period, drained by the slack of the frames within it. A tail builds a backlog the following frames drain; load whose mean exceeds the period builds it without bound. So on `variable_refresh` the band width is 0 (the dwell test and the pre-warm's switch test), and one backlog test replaces both downshift paths: `backlog = max(0, backlog + max(c, g) - N*period)` per frame at the current cadence, a downshift to `N + 1` once the backlog exceeds one cadence period (the cost of the longer cadence on every frame) while it is building - the frame added to a backlog that earlier frames left; an impulse (a stall, a single spike on a drained queue) builds it in one frame and the following frames drain it, which is the role of the attribution (C5) on a fixed grid. The rules belong together: without the band the upshift admits load whose N-1 cost the prediction at N cannot see (contention, thermal, work that scales with the rate), and the fixed-grid downshift rules sent the pacer back on a 10 % tail of such frames about once a second for good, although at N=1 those frames display on time or nearly so (q95 beyond T with near-miss pressure against the conservative deadline floor); a median statistic instead left real overload at N=1 for 60 frames to forever. The backlog drains under a sustainable tail and crosses one period after `T / (mean - T)` frames of overload (about 12 at 9 ms, 70 at 8.45 ms). At a load whose N=1 mean lies at the period the backlog is a zero-drift random walk and crosses at random times, often after the C10 survival window `4*T_up`, which then reset the backoff on every revert; on `variable_refresh` the window is `4 * dwell_required`, so each revert doubles the next window too. The limits: at such a load (mean within about 1 % of T at N=1, unseen at N=2) the pacer still alternates between N=1 and N=2 every few seconds in some seeds (mean present delta 9.5-10.4 ms, between N=1's 8.4 and N=2's 16.7 ms); a load whose mean lies just below T stays at N=1 with the drawable pool full (latency 16.7 ms against 15 ms at N=2); and a load the prediction cannot see is probed a finite number of times. Dropping the band also let the C30 heavy configuration complete its N=3 dwell; its pre-warm then ran on a GPU with no idle gap (N=3 and N=2 are both spaced at the deviation-24 bound, 2 slots, with 20 ms frames) and delayed a frame past the maximum refresh interval (a repeat). An upshift that leaves the target spacing unchanged prepares for no shorter interval and switches without a pre-warm. A continuous VRR cadence (targets spaced at the predicted frame interval when it exceeds T, so a load in (T, 2T) runs above half rate) is not needed for loads that fit T and stays open; `fixed_grid` is unchanged (C1-C29 identical).

## 9. Implementation notes
