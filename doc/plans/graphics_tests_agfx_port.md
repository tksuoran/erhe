# Port agfx GPU tests to erhe_graphics_gpu_tests

Status: in progress

Extends [`erhe/graphics_test_coverage.md`](../erhe/graphics_test_coverage.md)
and [`graphics_tests.md`](graphics_tests.md). The source is the agfx test
suite reviewed in
[`reference/agfx_comparison.md`](../reference/agfx_comparison.md) (agfx
commit `d8ad38b`, `<agfx>/src/agfx/agfx_tests/`); section 6 item 2 of that
document names golden-image testing as the second most valuable thing to
adopt, and this plan is that adoption plus the tests that come with it.

## 1. What "port" means

agfx registers 149 distinct tests (401 registrations across its C, C++ and
ez API flavors). Each is a small, single-feature GPU test: set up a few
resources, record one submission, read back, compare against a golden buffer
(byte-exact) or golden image (NVIDIA FLIP, mean error <= 0.05), often with an
analytic check as well. That shape is the same as the existing 38
`TEST_F(Gpu_test, ...)` cases, so a port is a re-authoring, not a copy:

- Every test is written against `Gpu_test` in GoogleTest, one erhe test per
  agfx test name, the C++/ez flavors collapsed (erhe has one API). The agfx
  test name is quoted in the test's comment so the two suites stay
  cross-referenceable.
- Shaders are GLSL inline in the test file (the existing convention), not the
  agfx HLSL. Push constants become a UBO binding; bindless handles become
  `Bind_group_layout` bindings; vertex pulling stays vertex pulling through an
  SSBO where the agfx test pulls, and uses `Vertex_input_state` where erhe's
  own path is the thing under test.
- Goldens are erhe's own, generated by the port and reviewed by eye on first
  commit. agfx goldens are not reused: shader language, NDC and texture
  coordinate conventions and the output routing (see 2.3) differ, so
  agreement with an agfx image is not a meaningful gate.
- No agfx source is copied. FLIP (2.2) comes as its own BSD-3 dependency
  from NVlabs, not from the agfx tree.

Tests are grouped into the phases of section 3 by the erhe feature they
cover; each phase is one commit series that ends with the coverage matrix
updated. Section 4 lists the agfx tests that are not ported and the erhe
feature each waits on.

## 2. Framework additions (phase 0)

The golden machinery lands first, in `erhe_gpu_test_support`
(`src/erhe/graphics/test/gpu_test_fixture.*`), because every later phase
uses it and because the existing image tests gain a second, stricter
assertion for free.

### 2.1 Golden assertions

Two helpers on `Gpu_test`:

- `expect_buffer_matches_golden(name, bytes)`: byte-exact compare against
  `src/erhe/graphics/test/golden/<name>.bin`. On mismatch the failure message
  lists the first differing offsets and the total count (agfx records up to
  4096); the output is written next to the artifacts (2.4).
- `expect_image_matches_golden(name, width, height, format, bytes,
  threshold)`: compares an RGBA8 (or RGBA32F, see 2.2) readback against
  `src/erhe/graphics/test/golden/<name>.png` (`.pfm` for float images) with
  FLIP, fails on a size mismatch or a mean error above `threshold` (default
  0.05, as agfx), and writes output, golden copy and FLIP error map to the
  artifact directory.

Both honour an update mode: the environment variable
`ERHE_GPU_TEST_UPDATE_GOLDENS=1` (read once by `Gpu_test_environment`) makes
the helpers write the golden instead of comparing and report the test as
passed with an "updated golden" note. This is the documented way to accept an
intentional rendering change; the diff is then reviewed in the commit like
any other change.

The analytic assertions the tests already make (specific texel values,
region equality, lit-pixel counts) stay. agfx's `test_compare.h` states the
reason: under update mode a golden records whatever the backend produced, so
a golden alone cannot catch a systematically wrong result. Every ported test
keeps at least one analytic check where agfx has one.

### 2.2 Image comparison metric

Image goldens are compared with NVIDIA FLIP from phase 0 on, as agfx does:

- The single header `cpp/FLIP.h` of `NVlabs/flip` (BSD-3) is fetched
  download-only through CPM at the top level, the way fpng is, and compiled
  into `erhe_gpu_test_support` only; no `erhe::*` library depends on it.
  `test_compare.cpp` in the agfx tree is the reference for the call:
  `FLIP::evaluate` with default parameters, `computeMean` on, the error map
  requested.
- RGBA8 outputs run LDR-FLIP on the normalized bytes; float outputs run
  HDR-FLIP (selected by the `.pfm` golden extension, agfx selects by
  `.hdr`). Alpha is dropped before the compare.
- The verdict is the mean error against `threshold` (default 0.05). The
  helper also records the maximum error and writes the magma-colored error
  map as the third image of the triptych (2.4).
- A one-pixel edge crawl between rasterizers (lavapipe against a hardware
  Vulkan device, GL against Vulkan) stays far under the threshold at 64x64
  to 128x128; a wrong color, a missing draw or a shifted region does not.
  Where a test needs an exact answer, its analytic assertion (2.1) gives it.

Golden images are read with the existing wuffs PNG loader and written with
the existing fpng writer (`Image_writer::create`); float goldens use a small
PFM reader/writer in the support library. The `ERHE_USE_FPNG=OFF`
configuration has no PNG writer, so the golden helpers `GTEST_SKIP` there
with that reason.

### 2.3 Output routing for compute-produced images

Nineteen agfx texture tests produce their image by writing an RGBA8 storage
texture from a compute shader. erhe's `set_storage_image` is Vulkan-only and
`image_2d` only (`Compute_command_encoder` header), so the port routes those
outputs one of two ways, chosen per test and stated in its comment:

- Sampling, gather, texture-load and comparison-sampler tests render a
  fullscreen triangle in a fragment shader into a color target (the
  `test_sampler_modes.cpp` pattern). Runs on Vulkan, OpenGL and Metal.
- Compute-only work (atomics, shared memory, multi-dispatch, ray query,
  buffer views) writes an SSBO and asserts a buffer golden; where the agfx
  test's image is the more readable artifact, the SSBO is copied into a
  texture with `copy_from_buffer` and asserted as an image golden as well.

Only the two tests that exist to exercise storage images themselves
(`UAVBarriers`, `WriteHDRTexture`) use `set_storage_image` with
`format_32_vec4_float`, and they `GTEST_SKIP` on OpenGL and Metal with
"storage images are Vulkan-only" as the reason.

### 2.4 Artifacts and report

A GoogleTest event listener installed by the test `main.cpp` writes
`<build>/gpu_test_results/results.json` after the run: device name, backend,
timestamp, summary counts and one entry per test (name, status, duration,
message, and for golden tests the artifact paths, the FLIP mean and maximum
error and the threshold). Per-test artifacts go to
`<build>/gpu_test_results/artifacts/<test name>/` as `output.png`,
`golden.png`, `flip.png` or `output.bin`, `golden.bin`. The listener is the
only writer of the JSON; the helpers only fill the per-test record.

`scripts/gpu_test_report.py <results dir>` renders `results.json` into one
self-contained `report.html` (images embedded as data URIs, no HTTP server):
header with device and counts, filter by status, and for each golden test an
output / golden / FLIP error map triptych; buffer tests show the differing offsets as
a hex view. It is Python because repository tooling is Python; agfx's
`tools/test_report/index.html` is the reference for what the page shows.

### 2.5 Backend differences

One golden set serves all backends. Where a backend legitimately differs
(GL's lower-left origin, cube face order, layered copy slice counts, the
cases in
[`erhe/graphics_test_nonheadless_port.md`](../erhe/graphics_test_nonheadless_port.md)),
the fixture normalizes at readback (`read_texture_rgba8` already returns
top-down rows on every backend) rather than keeping per-backend goldens. A
test whose device lacks the feature probes and `GTEST_SKIP`s with the
capability named, as `snorm_color_render_readback` does.

## 5. Verification and gates

Per phase, in this order, once at the end of the phase:

1. `erhe_graphics_gpu_tests` on `build_vs2026_vulkan_headless`: every test
   passes, zero validation messages (the fixture's `TearDown` already fails a
   test on any). Goldens are committed with the tests, reviewed in
   `report.html` before the commit.
2. The same binary on `build_vs2026_opengl`: every test passes or skips with
   a capability reason; the skips are listed in the coverage matrix.
3. `doc/erhe/graphics_test_coverage.md` gains one row per new test file and
   the total count in its header; `py -3 scripts/check_doc_links.py` clean.
4. Metal stays as in `graphics_tests.md`: builds, not yet run.

Phase 0 is verified by converting the two existing image tests with the
widest output (`test_texgen_render.cpp`, `test_msaa_resolve.cpp`) to also
assert a golden, running once to generate, editing one shader constant, and
confirming the failure shows in `report.html` with a correct FLIP error map.

The whole port adds about 107 tests to the 38 present.

## 6. Order and dependencies

Phase 0 first. Phases 1 to 4 are independent of each other and of 5 to 8 and
may run in any order; 7 needs nothing beyond phase 0; 8 needs a ray-query
device. Run the phases one at a time and commit each phase's tests, goldens
and matrix rows together, so a golden change is always in the commit that
caused it.
