# parsers/

Stability: mostly stable

## Purpose

File format importers for loading 3D content into the editor, plus the
erhe-authored glTF scene persistence entry points
(doc/editor/gltf_scene_roundtrip.md).

## Key Types / Functions

- **`import_gltf()`** -- Imports a glTF file into a `Scene_root` as an undoable compound operation. Uses `erhe::gltf` for parsing and creates meshes, materials, animations, and skins. **Asynchronous** (doc/editor/async_asset_loading.md): it queues an `Asset_load_task`, and the undoable operation is built from the finished parse once the load lands. `make_import_gltf_operation()` takes an optional `Prepared_gltf_parse*` for that; with `async_gltf_load` off it parses inline.

- **`finish_open_scene_gltf()`** / **`build_imported_buffer_meshes()`** -- The two halves the asynchronous path needs. `finish_open_scene_gltf` is the main-thread tail of `open_scene_gltf` (Scene_root construction, reference resolution, buffer-mesh finalize, content-library / physics / editor-state operations, node reparenting, raytrace kickoff); `build_imported_buffer_meshes` is the worker-side `Buffer_mesh` build, deliberately serial because mesh clones share `Primitive` objects and `make_buffer_mesh` has no per-shape serialization. `make_renderable_mesh` is idempotent, so the main-thread `finalize_imported_meshes` pass fast-paths over what the worker built.

- **Deferred load finalize** (doc/editor/async_asset_loading.md, `Load_config` in editor settings): with `deferred_edge_lines` / `deferred_raytrace` on (default), `finalize_imported_meshes()` builds only a fill-only buffer mesh straight from the triangle soup plus an AABB proxy raytrace (picking works immediately, on approximate bounds); the `Async_raytrace_kickoff_operation` then runs one background task per mesh that builds the Geometry (edges, smooth normals), the full buffer mesh and the real triangle raytrace, and swaps them in under the scene lock. A task whose shapes another task has already committed (an asset instanced many times shares one `Primitive` per shape) swaps nothing - `commit_real_raytrace()` and `commit_geometry_buffer_mesh()` say so by returning false - and then refreshes its own mesh alone instead of every mesh sharing the shapes, which is what keeps a load's commit cost linear in the instance count. `parallel_gltf_parse` gates parallel image decode / mesh parse / animation parse inside `erhe::gltf::parse_gltf` (`Gltf_parse_arguments::parallel`). Disabling the options restores fully eager, serial loading. Per-stage timings log under `editor.parsers` and `erhe.gltf.log`.

- **`save_scene_gltf()`** -- Scene save: one `export_gltf()` call writing the whole scene (render content + physics + prefab external assets + texture sources + animations + editor-domain `ERHE_*` extensions via `add_gltf_editor_state`) into a single `.glb`/`.gltf`. `ERHE_scene` in `extensionsUsed` marks the file erhe-authored. The `App_context&` overload is THE save entry point: it also sends `Scene_saved_message` and reloads the prefab when the written path is a loaded prefab source, so one Save Scene covers a prefab source too. `resolve_scene_save_path()` picks the destination: the scene's own source file when set, else `default_scene_dir()/<scene name>.glb`.

- **`open_scene_gltf()`** -- Scene open: opens an erhe-authored glTF file as a full `Scene_root` (not undoable; fresh empty `Content_library`; `ERHE_scene` payload applied: `enable_physics` at construction, ambient light, per-scene `Scene_settings`). Reuses the import machinery; no import_root wrapper, no default camera/lights.

- **`scan_gltf()`** -- Scans a glTF file and returns tooltip content lines, the structured `extensions_used` list, and the accessor-bounds AABB without loading buffer data. `is_erhe_scene()` checks `extensions_used` for `ERHE_scene`. It is still a whole-file read plus a full JSON parse, so callers on the main thread run it on a worker: the load path scans inside `Gltf_load_task`, and the asset browser through `ensure_scanned()` (`ensure_scanned_blocking()` remains for the drag-and-drop drop target, which needs the AABB in the same frame).

- **`import_physics()`** (`physics_import.{hpp,cpp}`) -- Turns the format-neutral `erhe::scene::Physics_description` every reader fills into editor physics, for both formats: the shared `Physics_material` / `Collision_filter` / `Physics_joint_settings` items, `Node_physics` attachments (rigid bodies and triggers, with the colliders below a body folded into its compound) and `Node_joint` attachments. Beside the description it takes what the reading format states of its own: per shared record a name, the erhe-only property values and the prim of the loaded tree the item is placed under, and per body the same values by node. A `Physics_import_item` with a parent is parented there and rides that tree's insert, like a material the file placed; one without gets a content-library attach operation, which is what creates its kind scope. A property list is either the item's complete local set (the glTF `ERHE_*` payloads, so a value outside it inherits again) or the values it names (a USD prim's `erhe:Owner:name` attributes, the rest being the description's own fields). A file states a property in either the bare or the qualified `Owner.name` spelling, and both resolve. `import_gltf_physics()` (`gltf_physics_import.cpp`) is the glTF entry: it fills the arguments from `Gltf_data` and its `ERHE_scene` / `ERHE_physics` payloads. Must run after mesh finalization (a mesh-sourced collision shape needs the built Geometry) and before the compound operation is composed.

- **`build_physics_description()`** (`physics_export.{hpp,cpp}`) -- The inverse, for both writers: the description of a scene's `Node_physics` / `Node_joint` attachments plus the content library's physics items that no body references, with `Physics_description_items` naming the library item behind each entry of the top-level arrays - which is what the glTF `ERHE_scene` physics_materials and physics_joints blocks and each record of a USD save need.

- **USD physics** (`usd.cpp`) -- `resolve_usd_physics()` hands `Usd_data::physics` and the stage paths beside it to `import_physics()` on both the import and the open-scene path, before the material attaches: a `Material` prim no mesh binds is a physics material prim, so the shading material the conversion made of it leaves the tree and the `Physics_material` item takes its place; a `PhysicsCollisionGroup` prim and a joint-settings prim are replaced the same way, and a joint that states its limits and drives inline gets a settings item in the `Physics Joints` scope under the joint's name. The guide prims whose shape has folded into a body leave the tree once the bodies are built. `apply_usd_physics_scene()` gives the scene's physics world the gravity the `PhysicsScene` prim states. On the save side `collect_usd_physics()` fills `Usd_save_arguments::physics` from `build_physics_description()`: the prim of the tree each record sits on, the erhe-only local values of that item as `Usd_physics_property` in the qualified `Owner.name` spelling with the USD type the reader hands back, and the physics world's gravity.

- **`gltf_extensions_export/import`** -- Editor-domain `ERHE_*` extension payload builders / appliers.

- **`import_usd()`** (`usd.{hpp,cpp}`) -- Imports a USD file (`.usd` / `.usda` / `.usdc` / `.usdz`, see `is_usd_file_extension()`) into a `Scene_root` as an undoable compound operation, through `erhe::usd` (`doc/erhe/usd.md`). Synchronous, unlike `import_gltf()`: there is no asynchronous asset-load path for USD yet, so `make_import_usd_operation()` loads, builds and returns the compound in one call and `import_usd()` queues it. The compound holds the content-library attaches for the textures, materials, skins and animations, the `Item_insert_remove_operation` that inserts the import_root node, and the raytrace kickoff - the same undo behavior glTF import has, including the removal announcements (doc/editor/import_undo_reference_clearing.md). It also owns the GPU side of USD textures: `erhe::usd` reports image FILES, and this loads them with `erhe::graphics::Image_loader` (PNG / JPEG / KTX2 / DDS) through a blocking-drain `Image_transfer` and fills the material slots the loader recorded. The whole file compiles to "USD support not built" stubs when `ERHE_USD_LIBRARY=none`, so no call site needs a conditional. Because the import and the open both run to completion inside one tick, their phases set breadcrumbs of their own (`usd: load stage`, `usd: textures`, `usd: finalize meshes`, `usd: composition arcs`, `usd: prefab template stage`, `usd: prefab template finalize`, `usd: content library`, `usd: attach to scene`): the stall watchdog reports the newest breadcrumb the tick thread set, so a phase that sets none is reported under whatever the tick passed through last - which on a large stage was the load's last raytrace BVH commit, and read as raytrace work that is not there.

- **USD composition arcs** (`usd.cpp`) -- `erhe::usd` reports the `references` / `payload` arcs a prim authors instead of flattening what they name (`doc/erhe/usd.md`, "Composition arcs"). Both the import and the open-scene path turn each arc into a `Prefab_instance` attachment on the carrier prim, in the arcs' order, with the arc's target cloned below it through `Prefab_library` (doc/erhe/usd_compatibility_design.md X1). A carrier is transformable - the import makes a typeless or `Scope` prim that authors arcs an `Xform` (`doc/erhe/usd.md`, "Composition arcs") - so what reaches the warning here is a carrier of a type that carries no transform, whose arcs are dropped. An internal reference names the stage's own file; a relative asset path resolves against the referencing layer's directory. A glTF-backed instance is sealed; a USD-backed one is not (doc/erhe/usd_compatibility_design.md X2), its structure alone being protected. The resolution runs before the insert operation is built, so an undo of the import removes the instances with the rest of the tree.
- **A `variants` selection an arc carries** (`usd.cpp`, `prefabs/`) -- A prim that references or payloads a target may author `variants` for the sets the target declares, and USD resolves that selection stronger than the target's own (doc/erhe/usd_compatibility_design.md C7; `doc/erhe/usd.md`, "Variant sets"). `Usd_reference::variant_selections` is what the carrier authors for what its arcs bring in; `to_prefab_variant_selections()` puts it in the editor's own terms (`Prefab_variant_selection`, `prefabs/prefab_instance.hpp`, which names no `erhe::usd` type because a prefab is a glTF file as readily as a USD one and `erhe::usd` is optional), and it travels three ways. The entries the target consumes are part of `Prefab_key`, so two carriers selecting different variants of one target prim load two templates - which is what USD composes, two prim indexes - while two carriers whose selections differ only in entries the target declares no set for share one template, and that chain is parsed once. What a template consumes is `Prefab::consumed_variant_sets`, which `load_usd_prefab_template()` reports: the sets `Usd_data::variant_sets` lists below the template's root prim, nested sets included, plus the sets the templates its own arcs brought in reported, re-rooted at the carrier that brought them in. `Prefab_library` reduces an arc's selection against what the templates of that file and prim consumed so far; the first load of a file has nothing to reduce against and reports what it consumed, and a file whose variant branches declare different sets can have a load consume a set that reduction dropped, which redoes that one load with the entry back in. It reaches `Usd_load_arguments::variant_selections` in `load_usd_prefab_template()`, rooted at the prim the arc targets. And `Prefab_instance` records it IN FULL - `attach_prefab_instance()` takes the arc's own selection, not the template's reduced one - so `collect_usd_references()` writes it back on the carrier and the round trip is a fixed point - the selection is written as it was authored, including one the target's layer answers for with a warning and drops.
  The selection also travels DOWN: `propagate_variant_selections()` hands the entries that name a prim to the arcs that prim authors, because a variant set is composed once out of the whole prim index and a selection for it is a selection for the opinions the prim's own arcs bring in as well. This is what makes `full_assets/Teapot/DrawModes.usd` compose: the `modelVariant` a column selects is declared in `Teapot.usd`'s root layer AND in the `Teapot_Geometry.usd` / `Teapot_Materials.usd` layers its payload sublayers, and only the propagated selection reaches the second pair. `Teapot_Geometry.usd` declares `modelVariant` and nothing below it declares `shadingVariant`, so the six shading columns share its two templates and the two `geo/*.usd` files are parsed once each: 25 templates for the file's 35 carriers. A selection the carrier authors itself loses to the one carried in, which is the outer opinion of one and the same set.
  An arc that names no prim path targets the file's default prim, whose path the file itself gives, so a selection cannot be measured from it until the file has been read: `load_usd_prefab_template()` then reads the file once without the selection and repeats the read with it. Only an arc of that shape that carries a selection at all pays for the second read.

- **Pending variant opinions** (`usd.cpp`) -- `apply_pending_variant_opinions()` applies what a variant authors for a prim a composition arc supplies (doc/erhe/usd_compatibility_design.md C6). `erhe::usd` cannot reach such a prim - the arcs of a file are instantiated here, after the load returns - so the reader hands those entries over as `Usd_variant::pending_overrides` / `pending_bindings` (`doc/erhe/usd.md`, "Variant sets") and this applies them. It runs on all three paths that instantiate arcs, right after `resolve_usd_references()`: the import path, the open-scene path and the template path (`load_usd_prefab_template`, which resolves the template's own arcs). The path is resolved the way an instance override's is, with `erhe::scene::find_instance_item` - one segment at a time, through the clone of every carrier it crosses - and every variant's entries are resolved, not only the selected one's, so the base values a later switch restores are what the prims held before that variant reached them. The applied entries move onto the variant's ordinary lists, so `fill_variant_table()` - which now runs after this - carries them into the scene's table. An opinion applied to a template prim reaches every instance of it through the reference layer (X2), which is what colors the seven teapot columns of `full_assets/Teapot/DrawModes.usd`: the `over` each `shadingVariant` block authors names a prim four arcs down.

- **USD draw modes** (`usd.cpp`) -- `resolve_usd_draw_modes()` turns every `Usd_draw_mode` record `erhe::usd` reports (`doc/erhe/usd.md`, "Draw modes") into local values of the prim the record names, with `Draw_mode.apply_draw_mode` stating that the prim carries the feature (`doc/erhe/property_system.md` section 4.24). It runs on the import, the open-scene and the prefab-template path, before the arcs of the file are instantiated, so a carrier's own values are there to be paired with its arc target's and a template's are there for its instances to read through the reference layer; on the two scene paths it is still before the insert operation is built, so an undo of the import takes the values out with the tree. A record whose prim is not part of the scene tree costs one warning. `set_draw_mode_source_directory()` then tells every prim of the loaded tree carrying a draw mode which file it came out of - the ones a variant opinion made included - which is what resolves a card texture a variant block spelled relative; a prim reading its values from a template already reads the template's directory, so nothing is written on it. `collect_usd_draw_modes()` is the save half: every prim of the tree carrying a draw mode with at least one authored value becomes a `Usd_save_draw_mode`, which the two-pass planner turns into a path. glTF carries the same values through `ERHE_node.properties` (D8), so a glTF save needs nothing of its own here. What the draw mode then draws - the pruning of the prim's children and the proxy in their place - is `scene/draw_mode_system.{hpp,cpp}` and `scene/draw_mode_renderer.{hpp,cpp}`, not a parser concern.

- **USD class prims** (`usd.cpp`) -- `resolve_usd_classes()` turns every `class` prim `erhe::usd` recorded into a `Style` item at the place the class prim has (a class under a `Scope "Styles"` becomes a style under that scope, a class inside a class a style under a style), applies the class's opinions with `erhe::scene::apply_property_values`, and makes each prim's first resolving `inherits` target its style (doc/erhe/usd_compatibility_design.md X3). Both the import and the open-scene path run it before the insert operation is built, so an undo of the import removes the styles with the tree.

- **USD brush prims** (`usd.cpp`) -- `resolve_usd_brushes()` turns every `Brush` prim `erhe::usd` recorded into a `Brush` item at the place the prim has, with the geometry the reader took from the prim's `Mesh` child (reprocessed for edges when it has none), the density and normal-style token it authored, the material its `material:binding` names, and its other authored opinions applied with `erhe::scene::apply_property_values` (doc/erhe/usd_compatibility_design.md E4a). A brush whose holding prim is in the loaded tree is parented there and rides that tree's insert, the way a material the file placed does; one the file gave no place gets a `make_library_attach_operation` of its own. `collect_usd_brushes()` is the save half: `erhe::usd` names no editor type, so each brush's geometry, density, normal-style token and material become a `Usd_save_brush` record for the writer.

- **USD node graph prims** (`usd.cpp`) -- `resolve_usd_node_graphs()` turns every marked `NodeGraph` prim `erhe::usd` recorded into the graph asset its `erhe:graph:format` token names - a `Graph_texture` for `erhe_texture_graph`, a `Graph_mesh` for `erhe_geometry_graph` - rebuilding the nodes through that kind's factory, the parameters from their (USD type, literal) pairs and the links by node and pin name, and leaves the graph dirty so the next frame's evaluation bakes it; the graph is parented where its prim sat, or gets a `make_library_attach_operation` when the file gave it no place, the way a brush is. It then binds what the file feeds from a graph: a material slot to a texture graph, and, from the `erhe:scene` block's `graph_meshes` entries, a prim to a geometry graph by writing that prim's `Geometry_graph_mesh.graph_mesh` value, plus that graph's display / ghost designation. `collect_usd_node_graphs()` and `collect_usd_graph_mesh_states()` are the save halves. The save side names a prim by the path `erhe::usd::plan_usd_prim_paths` plans for it - the save plans, fills the block, then writes with the same arguments - so the entry matches the reloaded item's path exactly; the same rule carries the variant selections. `doc/erhe/usd_node_graphs.md` owns the design (section 4 for a geometry graph), including why the bindings ride the scene block and how a pin or parameter name is spelled in a file.

- **USD skins** (`usd.cpp`) -- A skinned USD mesh reaches the scene the way a skinned glTF mesh does (doc/erhe/usd_compatibility_design.md K1). `erhe::usd` gives every skinned `Mesh` prim its `erhe::scene::Skin` and lists the skins in `Usd_data::skins` (`doc/erhe/usd.md`, "Skinning"); `append_usd_content_library_operations()` attaches each of them to the content library with a `make_library_attach_operation` of its own, tagged `"skin"` the way the glTF import tags its skins, so a skin is a library resource under the `Skins` scope and an undo of the import takes it back out with the tree. A skin has no place of its own in the prim tree, unlike a material the file placed, so it always gets an attach. Registration and the GPU build are the format-neutral paths: `Scene_root::register_mesh()` registers a mesh's skin with the scene (`mark_skin_joints` flags the joint prims, `Bone_visualization` builds its proxies on the `Skin_registered_message`) when the tree enters it, and `finalize_imported_meshes()` builds a mesh whose `skin` is set with the skinned `Build_info` so `Shader_key::derive` turns `USE_SKINNING` on. The joint prims are plain `Xform` prims of the loaded tree, so they ride the import's insert like any other prim.

- **USD content-library folders** (`usd.cpp`) -- A USD file carries the scene's folder tree as the `Scope` prims it is (doc/erhe/usd_compatibility_design.md E4d), so both the import and the open-scene path hand the tree to `Content_library::adopt_kind_scopes()` before they build the attach operations of the resources they read: each of those resolves the scope its resource goes into as it is constructed, while the loaded tree only enters the scene with the insert at the end, so without this the load would make a second `Materials` scope beside the one the file brought back. A kind scope is recognized by its name in either spelling, the editor's or the stage's (`Graph Textures` / `Graph_Textures`).

- **USD variant sets** (`usd.cpp`) -- `fill_variant_table()` turns every material-binding `variantSet` `erhe::usd` recorded into an entry of the target scene's `Variant_table` (`scene/variant_table.hpp`, doc/erhe/usd_compatibility_design.md X4): the carrying prim and each binding's Material prim are held weakly as the items the load made, so a later switch assigns them without re-reading the file. The reader has already bound the selected variant, so an import needs no switch; the open-scene path then calls `Scene_root::apply_variant_selections()`, which applies a `Scene_settings::variant_selections` entry that names a different variant than the file's `variants` metadata did. `collect_usd_variant_sets()` is the save half: the table with its current selection becomes `Usd_save_arguments::variant_sets`, and a set whose file variants authored opinions beyond material bindings is named in one warning per save, because those opinions are not written. A set a variant block declares is carried with the block that declares it (`enclosing_set_name` / `enclosing_variant_name`, both empty for a set the prim declares itself), which is what names it in the table, in `Scene_settings::variant_selections` and in the MCP tools - `doc/editor/scene.md`, `Variant_table`, owns what a switch of such a set does.

- **glTF material variants** (`gltf.cpp`, `gltf_extensions_export.cpp`) -- `fill_gltf_variant_table()` turns the asset's `KHR_materials_variants` list into ONE entry of the target scene's `Variant_table`, named `c_gltf_variant_set_name` (`materials`, `parsers/gltf.hpp`), because a glTF asset holds one asset-wide variant list (doc/erhe/usd_compatibility_design.md X4). The carrying prim is the import root on the import path - the prim an undo of the import removes, which takes the set out of the table with it - and the scene's own root prim on the open-scene path, where the file's content sits in the root's place. Bindings name a primitive by index (`<mesh path>#<primitive index>`, `scene/variant_table.hpp`), since glTF gives a primitive no name of its own. glTF authors no selection, so the set starts with none selected and the primitives keep the materials the file gave them until the user picks; the open-scene path then calls `Scene_root::apply_variant_selections()` for the `ERHE_scene` entry. `find_exported_variant_set()` + `collect_gltf_material_variants()` are the save half (doc/editor/scene_serialization.md step 5b), and the `ERHE_scene` settings are serialized from a copy whose `variant_selections` holds the written set's entry under the empty (root) prim path - the path the reloaded scene carries that set on.

- **`load_usd_prefab_template()`** (`usd.{hpp,cpp}`) -- The USD branch of `Prefab_library::load_template`: loads the file, creates its textures, finalizes its meshes, instantiates the arcs authored inside the template subtree (recursively, through the same library, so a cycle is caught there) and returns the prim the arc named wrapped in an unhosted template root. The
target is any prim (doc/erhe/usd_compatibility_design.md S1): an `Xformable`, a
`Scope`, the `Typed` prim a typeless `def` or an unrecognized `typeName`
becomes, or a prototype a `class` prim holds (X3). The wrapper keeps the
target's authored local transform when the target is an `Xformable` and simply
holds it otherwise - a prim without a transform composes what reaches it
through to its children. At instantiation (`attach_prefab_instance`) a
carrier that authors an xformOp stack of its own supersedes that transform:
the target's clone takes the identity, because `xformOpOrder` is one
attribute and the referencing layer's wins wholesale (usd-wg
InternalReferenceTest authors scale 100 on both the prototype and every
instance, and composes to one). A prototype target is content-less where it sits, so
the template it becomes gets `Item_flags::content` back on every prim of the
file it holds.

- **`import_geogram()`** -- Imports Geogram mesh files.

- **`import_wavefront_obj()`** -- Imports Wavefront OBJ files.

- **`Json_library`** / **`json_polyhedron`** -- Loads polyhedra definitions from JSON (used by `Scene_builder` for Johnson solids and other named polyhedra).

## Public API / Integration Points

- `import_gltf()` is called from scene loading and asset browser
- `save_scene_gltf()` / `open_scene_gltf()` back File > Save Scene / Load Scene (via the `load_scene_file` message handler in operations_window.cpp) and the MCP `save_scene` / `load_scene` tools
- `scan_gltf()` is used by the asset browser to preview file contents and by the load path to branch erhe-authored vs foreign glTF; both run it off the main thread
- Imported content is added to the target `Scene_root` and its `Content_library`

## Dependencies

- erhe::gltf, erhe::geometry, erhe::primitive, erhe::scene
- editor: App_context, Scene_root, Content_library, Asset_manager (asynchronous loads)
